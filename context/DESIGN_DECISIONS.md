# Design Decisions

Decisions recorded before implementation, based on the approved product brief.

| Decision | Rationale | Implication for the build | Date added |
|---|---|---|---|
| Design FieldOps Command as an attention-management product rather than a comprehensive telemetry display. | Managers need to identify changing conditions and move work forward, not sift through every data point. | Lead with operating condition, changes, regional risk, and prioritized assets; keep detail relevant to action. | 2026-11-01 |
| Treat the Regional Operations Manager as the primary user. | The MVP must support a clear decision-making role rather than dilute focus across all operational roles. | Optimize the overview and asset workflow for regional review and coordination; treat supervisors and operators as secondary context. | 2026-11-01 |
| Prioritize operational attention over generic KPIs. | Metrics matter when they help explain condition, change, risk, or action. | Present metrics in an operational narrative and connect them to prioritized assets and context. | 2026-11-01 |
| Make priority explanations transparent. | Managers must understand why an asset requires attention; priority is not autonomous AI. | Show material supporting reasons and avoid mysterious scores or unsupported predictive claims. | 2026-11-01 |
| Design desktop-first with tablet support. | The primary use context is operational leadership review, with the need to remain usable on tablets and small screens. | Establish a readable desktop hierarchy and reflow information by priority at narrower widths without horizontal page scrolling. | 2026-11-01 |
| Use a restrained operational visual system. | The experience should feel credible, calm, focused, precise, and actionable. | Use neutral surfaces, one operational blue, amber for attention, red for critical conditions, green for verified healthy or completed states, and text or icons in addition to color. | 2026-11-01 |
| Do not include an unnecessary map in the initial MVP. | A map adds value only when it supports a specific operational decision. | Prefer region comparison and prioritized asset views; add a map only if a defined decision requires it and approval is obtained. | 2026-11-01 |
| Make the selected region and period the shared scope for overview metrics, regional display, the change statement, and prioritized assets. | Filters should update the full operational narrative consistently rather than only one panel. | Derive the whole overview from one selector result; selecting a region narrows regional comparison to that region, while All Regions displays all four. Order regional comparisons by calculated operational status, priority, and exception attention, with deterministic name tie-breaking. | 2026-11-01 |
| Generate the management signal from the largest known production gap and current priority context. | The fixture contains one current snapshot and no historical priority count to support a truthful critical-exception increase/decrease claim. | State the region with the largest known target gap for the selected period; qualify incomplete telemetry and avoid inventing historical exception movement. | 2026-11-01 |
| Withhold production attainment when the selected scope has missing readings. | Treating unknown production as zero or calculating against partial coverage could mislead operational decisions. | Show known production totals with an explicit incomplete-telemetry note; show attainment as unavailable until coverage is complete, and visually subordinate partial totals when telemetry is incomplete. | 2026-11-01 |
| Make Asset Detail the Operations Overview's second-level workflow, while delivering action execution in a separate increment. | Managers need to move from prioritized attention to supporting evidence, current work, and an intervention decision without making the detail view feel like a different application. | Use the route asset ID to display identity and condition, explain priority before supporting evidence, then show existing work, a state-based intervention cue, and recent events. Keep acknowledgement and crew assignment non-functional until their separately approved implementation increment. | 2026-11-01 |
| Establish an independent FieldOps Command visual system with semantic palette, a single Roboto UI typeface, and the supplied TerraVale Energy logo. | A consistent, accessible operational UI should be recognizable without inheriting branding or screen structures from inspiration references. | Use navy for brand structure, operational blue for interaction, deep blue for secondary structure, and reserve action red for critical status. Use Roboto throughout, bundle its required Latin weights locally, and retain a system sans-serif fallback. Establish hierarchy through weight, size, spacing, and restrained uppercase labels. Display the supplied logo proportionally on the navy header, keep FieldOps Command as a separate product name, and use lightweight outlined SVG icons without adding an icon dependency. Keep prototype and synthetic-data disclosures out of the product UI while retaining fictionalization requirements in project documentation and data. | 2026-11-01 |
